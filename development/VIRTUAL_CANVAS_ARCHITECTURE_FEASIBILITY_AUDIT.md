# Virtual canvas architecture feasibility audit

Date: 2026-10-26. Mode: read-only investigation. Decision: REVISE the architecture proposal; NO-GO for implementation authorization or B1 production promotion.

## Scope and evidence standard

This report reads the current dirty Screensaver and Universe checkouts. No renderer, fixture, shader, installation, profile, journey, or display state was changed. The report itself is the sole new file. Source-derived statements below describe this checkout, not an installed build. Prior B1 measurements are identified separately. No new runtime or GPU residency measurement was made. Screensaver `BUILD_FROM_SOURCE.md` and both local `AGENTS.md` files were read.

The important distinction is that the installed host path selects a rectilinear panorama. Cylindrical projection requires a developer build plus a document-start bootstrap contract (`Universe/src/reach/ReachDeveloperProjection.ts:9-30`, `Universe/src/main.ts:160-162`, `Universe/src/core/Engine.ts:51-63`). B1 acceptance remains NO-GO. Thus the resource model below is for a hypothetical cylindrical implementation based on the current developer renderer, not current installed residency.

## 1. Current path and ownership

```text
Windows EnumDisplayMonitors/GetMonitorInfoW, virtual-screen metrics
  -> DisplayLayout physical rectangles and primary flag
  -> one borderless Form and WebView2 control per monitor
  -> one shared WebView2 environment/profile, distinct page and WebGL canvas per Form
  -> injected panorama contract: desktop bounds, local offset, physical width/height, DPR
  -> primary Reach voyage and camera pose -> BroadcastChannel -> follower poses
  -> rectilinear production: camera.setViewOffset -> scene/composer/black-hole/bloom/output
  -> cylindrical developer: global sector identities -> per-window sector targets
     -> optional cube -> cylindrical ray/lens -> padded bloom/output -> local crop
  -> WebView2 composition into each physical monitor window
```

- `Screensaver/Display/DisplayLayout.cs:17-27,31-44` sorts displays left to right and chooses the middle item as `VisualAnchorMonitor`. This is **not** the Windows primary. The field is used for logging and the legacy/native `SpaceRenderer` focal anchor (`Rendering/SpaceRenderer.cs:53-55`), while the WebView2 panorama passes `DisplayRegion.IsPrimary`. A future virtual-canvas contract must explicitly use the Windows primary, not `VisualAnchorMonitor` or a numeric monitor ID. `QueryWindows` obtains actual monitor rectangles, primary flags and effective DPI from Win32, then the bounding virtual rectangle from system metrics (`DisplayLayout.cs:93-153`; `Native/Win32.cs:40-71`). Negative origins are retained. The executable manifest declares PerMonitorV2 DPI awareness (`app.manifest:22-27`); WebView2 startup also calls `SetProcessDpiAwarenessContext` before display enumeration (`Application/ReachWebApplication.cs:83-94`). Code evidence, not a fresh coordinate observation.
- The host validates one primary and every monitor inside virtual bounds (`Application/ReachWebApplication.cs:150-164`). It creates a group of fullscreen windows, primary first (`:322-382`), with physical `Bounds` (`:472-508`). The group uses one `CoreWebView2Environment` and user-data folder (`:352-359`), but each Form owns a separate `WebView2` control (`:460`, `:602-615`) and page. The contract injected before navigation contains monitor and virtual rectangles and offsets `monitor - virtual origin` (`:167-171`, `:852-887`). `ValidatePanoramaStatus` checks the applied offsets and dimensions (`:173-194`). Each local canvas still needs CSS-size times DPR to equal physical pixels; the developer host checks this explicitly (`Application/ReachDeveloperApplication.cs:979-1018`). Effective DPI is coordinate plumbing, not physical-size calibration.
- `Universe/src/reach/ReachPanorama.ts:45-77` validates the contract and applies a global rectilinear `PerspectiveCamera.setViewOffset(fullWidth,fullHeight,offsetX-shiftX,offsetY,localWidth,localHeight)`. `reachCompositionTarget` uses the primary rectangle center plus bounded per-destination horizontal variation (`:80-89`). Only the primary owns a journey store (`Universe/src/main.ts:166-172,349-362`); it publishes camera pose, time and composition shift through `BroadcastChannel` (`ReachPanorama.ts:113-136`, `main.ts:1455-1465,1506-1534`). Followers update their own scene and render after receiving a frame (`main.ts:1580-1611,1711-1714`). The state is authoritative but simulation, scene objects and GPU resources are still per page.
- Normal rendering is `Engine.render`: scene directly or scene -> `BlackHolePass` -> `UnrealBloomPass` -> `OutputPass` in `EffectComposer` (`Universe/src/core/Engine.ts:80-91,169-176`; `src/render/BlackHolePass.ts:13-33`). Each page sizes its renderer and composer from local CSS size and DPR (`Engine.ts:108-120`). This rectilinear path has a logical global projection, yet it is not B1's cylindrical lens solution.
- Developer cylindrical rendering uses `CylindricalRenderer`: focal length from **virtual desktop height**, global sector centers from desktop width and shared shift, local selection from an expanded display rectangle (`Universe/src/reach/CylindricalGeometry.ts:4-69`, `CylindricalRenderer.ts:210-242`). It renders the scene once per selected sector, plus six cube faces when the black hole is enabled (`CylindricalRenderer.ts:251-269`). `warpFragment` is the non-lens shader entry (`:32-56`). `createCylindricalLensMaterial` reuses the production black-hole fragment but substitutes cylindrical `rayDir` and background lookup (`src/reach/CylindricalLens.ts:4-78`); sector/cube selection is at `:28-53`. The original black-hole shader's geodesic/disc path remains `src/render/shaders/blackhole.frag:66-171`. The padded local lens image goes through bloom and output, then a crop shader presents only that monitor's rectangle (`CylindricalRenderer.ts:274-303`). The accepted B1 fixture used a 512-pixel guard; the developer default outside those fixtures is 128 (`Application/ReachDeveloperApplication.cs:181`; `CylindricalGeometry.ts:7`). Native bloom mip origins are not globally aligned by default; `alignedBloomRect` is a separate diagnostic mode (`CylindricalGeometry.ts:60-72`).

Layout-independent pieces already present: Windows rectangle enumeration; negative-offset contract; primary-led sync; global rectilinear view offset; cylindrical global sector identity calculation; local output crop. Arrangement-dependent pieces: `DisplayLayout.VisualAnchorMonitor` chooses horizontal middle; cylindrical focal/sector resolution depend on **bounding height**, not occupied display area; per-display sector lists differ; padded post rectangles can cover empty regions; native bloom mip grids can disagree at joins. The production group is initialized once and has no display-change handler; only the developer group re-queries layout (`Application/ReachDeveloperApplication.cs:813-820`). Dynamic topology behavior is therefore unproved and likely requires group teardown/recreation, not an in-place offset change.

## 2. Duplication and B1 evidence

Source-derived for cylindrical mode: each monitor has its own scene, renderer, sector targets, optional 512x512x6 cube, composer pair, bloom targets, output canvas and overlay. One scene render occurs per selected sector, and six more occur when `BlackHolePass.enabled` (`CylindricalRenderer.ts:210-269`). Sector targets use RGBA16F, depth and up to four samples (`:225-236`). The source dimensions are `ceil(2*focal*tan(35 deg))` by `ceil(2*focal*tan(30 deg))` (`:210-218`). Every WebGL context has its own WebGL texture objects. Browser/driver image-cache or physical backing reuse was not measured; shared WebView2 environment is **not** evidence of shared WebGL targets or scene assets. Source rendering cannot currently be shared across contexts because no GPU interop/export path exists in either checkout.

For the recorded 8320x2160 layout and the R9 `hole-26-left` state, the global identities were -107.994, -57.994, -7.994 and +42.006 degrees. Left selected the first three, primary the middle three, right the last two (`Screensaver/development/STAGE_B1_R10_LAYOUT_GEOMETRY.json:76-140`). Eight target instances represent only four distinct global directions; -57.994 and -7.994 occur in multiple contexts. At black-hole frames this is eight sector scene renders plus 18 cube-face scene renders. R9 measured 142 full-frame draw calls on the left, rising to 156 when adding one sector, and 142 on primary; the 14-call delta is measured for that scene/pose, not a universal draws-per-sector constant (`STAGE_B1_R9_FULL_FRAME_SECTOR_PARITY_PILOT.md:68-82`). Right-window total draw calls and asset residency were not established by that measurement. Bloom and final output are repeated per window (`CylindricalRenderer.ts:113-125,291-303`).

R8 isolated the positive-yaw discontinuity to cube fallback on left versus perspective sector on primary at the same virtual ray; forcing the same representation matched across contexts (`STAGE_B1_R8_SOURCE_PATH_PARITY.md:49-59,124-140`). R9 added one 3244x2675 sector on left; the frozen +6.815-degree join mean fell from 2.917 to 0.967 encoded-luma units and rows above 20 from 59 to 3, for 99.31 MiB nominal color-plus-depth and 14 added scene draws (`STAGE_B1_R9_FULL_FRAME_SECTOR_PARITY_PILOT.md:30-49,68-82`). R10 found motion-time activation cannot yet guarantee no source popping (`STAGE_B1_R10_MOTION_SECTOR_COVERAGE.md:149-171`). R11 showed the main negative-yaw caustic peak is adjacent-ray disc emission, reproducible inside a context, not a cross-context source mismatch (`STAGE_B1_R11_NEGATIVE_YAW_ROOT_CAUSE.md:35-84`). R12's zero-target blend created screen-fixed ghosting and worse joins at other yaws (`STAGE_B1_R12_ZERO_TARGET_FEASIBILITY.md:45-83`). These are bounded developer-fixture observations, not owner visual acceptance.

## 3. Feasibility and alternatives

A virtual canvas should be a coordinate and sampling contract: for desktop pixel center `(x,y)`, set `(u,v)=(x-virtualLeft+0.5,y-virtualTop+0.5)`; primary composition comes from its **physical** rectangle. Each monitor renders only its own rectangle plus a bounded postprocessing halo. This handles negative origins, vertical placement, mixed resolutions and noncontiguous rectangles geometrically. Empty desktop gaps need no final pixels, although a source sector or padded halo can still cross a gap. The same global camera, focal/projection rule, sector IDs, source path and time must be used for equal virtual coordinates. A logical canvas does not imply one GPU framebuffer or one WebGL context.

| Option | Feasibility and B1 effect | Work and memory | Risk / deployment |
| --- | --- | --- | --- |
| A. Existing per-monitor WebView2, globally consistent source and sector selection | Feasible in the current host. Matching source identity and representation can address R8/R9 positive-yaw mismatch, but ray-deflected lookup can request offscreen identities; naive join-only closure fails R10. Does not remove R11 intrinsic caustic. | Context, scene, cube, bloom and assets remain duplicated. Static union sectors can be expensive. | Medium renderer risk; no new native presentation stack. Needs runtime coverage proof. |
| B. One large WebGL/WebView2 rendering context, crop/present to monitors | One source context is conceptually simple, but a single fullscreen WebView spanning the desktop would draw gaps and can exceed WebGL target limits. Splitting one WebView's live surface into independent monitor HWNDs is not provided by the present WinForms WebView2 usage. CPU readback/copy is unsuitable as a 60-fps HDR design. | Could avoid duplicate source work only if a supported low-latency GPU presentation bridge is demonstrated; giant lens/bloom buffers scale with bounding extent. | High native rewrite and compositor/timing risk; reject as the primary plan. |
| C. Central GPU source renderer plus separate WebView2 presenters | No source-export/import API or cross-context texture-share implementation was found in either repo. A common WebView2 environment shares browser infrastructure, not application WebGL texture handles. Native D3D shared-texture interop would require a new, proven pipeline and likely a different renderer/presenter contract. | Potentially lowest source duplication, but unquantified synchronization, copies, color/HDR and residency. | Research only; reject for implementation now. |
| D. Common camera/scene state and global source identity, bounded per-monitor rendering | Recommended revision. Retain physical windows and the accepted ray/lens equations; formalize one global projection/sampling contract and local crops. Source selection must remain stable over a validated ray envelope or use a representation that is globally identical without an unbounded sector union. | Still duplicates scene renders; can bound local post work and avoid desktop-sized output. Performance must be measured. | Medium to high Universe refactor; modest host contract work; credible path to R8 correctness, pending R10 and budget gates. |

Microsoft describes controls under one `CoreWebView2Environment` as sharing a browser process/user-data folder and potentially renderer processes; it does not grant shared WebGL texture objects ([WebView2 environment/controller/core](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/environment-controller-core?tabs=win32cpp)). Composition controllers offer a different host presentation API, not a demonstrated WebGL texture-export route ([WebView2 API overview](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/overview-features-apis)). GPU source-sharing feasibility remains unsupported, not proven impossible for all future native designs.

## 4. Resource comparison

Model assumptions: cylindrical mode, black-hole cube active, full-resolution DPR output, 50-degree vertical FOV, native bloom, 512-pixel guard, primary-centered shift with zero per-stop variation. This shift is `primaryCenterX - virtualWidth/2` (`ReachPanorama.ts:80-89`); live destination variation can change exact sector membership by up to 0.1 primary widths. Rectangles are `[x,y,width,height]` in virtual coordinates. Existing three are `[0,0,3840,2160]`, `[3840,720,2560,1440]` (Windows primary), `[6400,1080,1920,1080]`. Fourth is assumed `[0,-2160,3840,2160]`, directly above the left display. After origin normalization its y is 0 and the other three y values increase by 2160. This yields a bounding 8320x4320 desktop with large empty areas. Dual uses the first two rectangles and takes the 3840x2160 display as primary. These assumptions do not claim to be the owner's fourth-monitor layout.

Principal bytes use the code's formula: `12*sum(sector pixels) + 12*6*512^2*monitorCount + 16*sum(padded post pixels)` (`CylindricalRenderer.ts:144-149`). This counts sector color/depth, cube color/depth and composer pair. It excludes bloom mips, browser surfaces, scene textures, assets, driver metadata and multisample attachments. The upper planning number below adds four more nominal sector footprints to expose sensitivity to four-sample storage and resolves; it is **not** a measured or guaranteed GPU upper bound. Actual residency could exceed it.

| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| Single 3840x2160 | 2; 2 | 3244x2675 | 17.36 M | 6 | 8.29 M | 343-1138 MiB | 8 |
| Dual 6400x2160 | 3+2; 5 | 3244x2675 | 43.39 M | 12 | 15.40 M | 768-2754 MiB | 17 |

These counts were calculated directly from `sectorCenters`, `displaySectorCenters` and `paddedDisplayRect` with the stated assumptions (`CylindricalGeometry.ts:12-58`). Each cube adds 1.573 M face pixels per window per frame when active. The post-pixel column is the sum of padded rectangles for **one** full-resolution pass; composer, bloom mips and crop issue multiple passes, so it is not total fragment workload. The recorded R9 center offset was +1216 px, not the table's +960 primary-center baseline; it still yielded 3+3+2 at three monitors. Full-frame draw count cannot be predicted by a fixed multiplier because visible objects and passes vary. The R9 14-draw sector increment provides only a scene-specific scaling example: nominal sector draws would be 28, 70, 112 and 98 in these rows at that same 14-draw scene complexity, **excluding** cube and post draws.

Cross-check: A2-R4's earlier calculation for the existing three displays at native bloom and 512 guard reported 794.47 MiB sectors + 54.00 MiB cube + 309.27 MiB composer = 1157.74 MiB before bloom, matching this table after rounding. It added 141.65 MiB bloom for 1299.38 MiB calculated target payload, still excluding multisample, driver and assets (`Screensaver/development/STAGE_A2_R4_RESULTS.md:138-158`). This is a prior source calculation, not measured GPU residency.

Costs scale differently: context count, six-face cubes, browser surfaces, scene GPU objects and per-window bloom scale with monitor count; sector targets and scene draws scale with selected sector instances; target dimensions scale with global focal length, hence virtual height; local canvas scales with each monitor's native resolution; full-desktop allocation would scale with bounding extent including gaps. Current `paddedDisplayRect` and sector rendering can still process some empty area, so the revised design must bound halos and source coverage rather than promise zero processing of every empty pixel. Maximum texture size and eight-sector cap can reject extreme layouts (`CylindricalRenderer.ts:187-241`, `CylindricalGeometry.ts:7,29-37`).

## 5. Correctness and migration contract

Acceptance must be checked with exact virtual pixel-center mapping and an identical pose/time/scene state: (1) the same global coordinate yields the same pre-lens source identity, representation and sampled value in either window; (2) both horizontal and vertical physical joins are continuous under moving lens and bloom, with same-coordinate cross-context probes separated from adjacent-pixel gradients; (3) no screen-fixed transition, ghost or target-allocation pop anywhere in a monitor; (4) primary framing follows the Windows primary after negative-origin or monitor-ID changes; (5) single, dual, existing three, fourth-above, mixed-resolution and gap layouts are stable, and topology changes restart or rebind safely; (6) no whole-bounding-desktop post target when regions are empty; (7) measured per-process GPU residency, per-context memory and frame-time percentiles remain within a budget fixed before implementation. R11's steep adjacent-ray caustic can legitimately make neighboring physical pixels very different; a matching-source same-coordinate test distinguishes it from a window boundary fault.

Reuse: host Win32 enumeration, primary flag, DPI manifest, fullscreen windows, profile isolation, native input exit, offline mapping and panorama contract shape; Universe primary-led voyage sync, global rectilinear offsets, cylindrical ray/lens mathematics, source-sector math and local crop. Refactor: primary anchoring where `VisualAnchorMonitor` or bounding-center assumptions leak in; a single layout/camera/source specification shared by all pages; sector coverage/representation policy; physical-pixel scaling checks; topology lifecycle; post/bloom coordinate alignment. The 512 guard is a fixture-specific accepted setting, not proof for every layout or mip mode. Preserve black-hole geodesic and disc equations, destination shift behavior, native bloom look, overlays, tile-camera LOD and single-monitor quality. A fourth monitor's doubled virtual height currently multiplies target resolution and lens focal length, so alternative focal/coverage rules require visual validation and cannot be silently substituted.

Host regression surfaces: fullscreen group startup, native input exit, Settings and `/p` embedded preview, display-change shutdown, shared profile and journey/reset confirmation. Universe regression surfaces: primary-only checkpoint writer and migration (`src/main.ts:166-172,455-457`; `src/reach/JourneyState.ts`), followers, destination framing, black-hole uniforms, cube fallback, mip alignment, tile LOD, explorer path and offline resources. A renderer-only change should not require a journey schema migration, but installed state compatibility must be verified with an isolated copy of existing-schema fixtures. No owner journey or production profile should be used as a test fixture.

## 6. Recommendation and smallest proof

**REVISE.** Keep a continuous **logical** virtual canvas, Windows-primary anchoring and bounded per-monitor WebView2 presentation. Do not authorize a giant framebuffer or native GPU-sharing rewrite. Do not implement a static all-sector union as the long-term answer: the fourth-above model exposes multi-GiB nominal costs. The positive-yaw representation mismatch is tractable in principle through globally consistent sources, but the source policy and bounded memory contract are not proved. R11's caustic is a separate visual-fidelity issue. B1 remains NO-GO.

Smallest isolated proof of concept, if authorized later: in a disposable profile and fixture only, hold the accepted lens equations and a frozen black-hole state, run two existing physical windows, and render a narrow identical virtual strip in both contexts using one explicitly shared sector-identity/source policy. Compare same-coordinate lens and final pixels, both joins where available, then move yaw continuously while recording full-frame changes, target counts, draw calls, frame times and GPU residency. Add a fourth-above layout **geometry calculation** before any fourth-window rendering; reject if targets exceed a pre-agreed memory/texture-size cap. Preserve all forensic captures. This is a proposed experiment, not work performed in this audit.

Implementation authorization should require: an agreed primary-anchored pixel/ray contract; a source policy that passes the R8/R9 positive-yaw parity and R10 motion entry/exit cases without R12 ghosts; explicit single/dual/three/fourth-above limits; measured memory and frame-time budgets on target hardware; horizontal and vertical join captures with native bloom and 512 guard; negative-yaw caustic classification without false seam fixes; topology-change, preview, single-monitor and journey-restoration regression checks; owner visual acceptance. Until then, no production promotion.
