# R19 two-axis source tiling feasibility

Date: 2026-10-28. Mode: read-only architecture investigation. No renderer, shader, fixture, display, installation, journey, or Git state was changed. B1 remains NO-GO.

## Decision

**REVISE the research direction; NO-GO for implementing the modeled two-axis scheme as a B1 candidate.** Bounded vertical perspective slabs are geometrically possible and could remove the single tall-target dependency. Under a stable primary X/Y anchor and a fixed 1440-pixel focal reference, a concrete full-center-density model reduces nominal 2x-MSAA sector storage for the fourth-above layout from about 8260 to 4403 MiB. It also raises perspective scene renders from 14 to 32 across the four WebView2 windows, before lens-driven extra coverage. In the existing three-monitor layout, it raises renders from 10 to 20 and nominal storage from 2360 to 2752 MiB relative to an equivalent single-tall-source, primary-anchored model. This is not a convincing general memory/throughput improvement. It is only a conditional vertical-layout research lead, pending a smaller adaptive-band design and proof that lens rays can use one source representation without popping.

These are source-derived geometry and allocation estimates, not measured GPU memory or draw workload. The current R13 three-monitor cylindrical appearance remains the visual reference. No R19 images, GPU counters, shader compilations, or owner visual acceptance were produced.

## Projection policy: four independent decisions

1. **Optical anchor.** Use the actual Windows primary rectangle, with an explicitly shared horizontal composition offset, for X and Y. In this model `Cx = primary.x + 0.6 primary.width` (the R13 fixture's primary center plus 0.1 primary width) and `Cy = primary.y + primary.height/2`. This holds the vertical composition to the primary when a monitor is added above. It requires one authoritative anchor in all contexts.
2. **Angular pixel scale.** The model uses `f = 1440/(2 tan 25 deg) = 1544.045` physical pixels, held fixed as layout changes. This is R18's stable reference policy, not the current R13 focal of 2316.067 pixels. At the same scene pose, objects are therefore smaller on the existing layout; tiling does not reverse that. An alternative `f` based on current primary height gives a 50-degree primary vertical span but changes scale when the primary changes and creates a nine-sector horizontal case in R18's mixed layout. Neither policy has owner visual acceptance.
3. **Angular source coverage.** Choose the horizontal centers and vertical bands from actual physical monitor rectangles plus the 512-pixel fixture guard and a bounded lens-ray envelope. Coverage is a set of directions, not the whole virtual bounding rectangle by default. Empty desktop gaps need no direct output rays, but lens-deflected rays may point into them.
4. **Source raster resolution.** At each tile's central perspective coordinates, retain approximately one source texel per physical output pixel, as in the current full-density sector rule. Do not shrink raster dimensions to force a memory target. Off-axis Jacobians, star point-size shaders, filtering, MSAA resolve and bloom still require rendered acceptance.

The R13 appearance cannot be held exactly while changing `f` or the optical origin. A fair pilot would first compare a tiled source against a single-source control with the **same** new X/Y anchor and focal, then compare that projection with the R13 native reference. The current production renderer remains rectilinear.

## Candidate geometry and source selection

Architecture A is the existing horizontal-only 70 by 60 degree perspective sectors. It has one source target per selected sector. A fourth-above layout doubles virtual height, doubles `f`, and makes each target roughly four times the area. An R18-style primary-anchored A variant holds `f` fixed but needs one tall vertical FOV per sector; the fourth-above model reaches 2163x7945.

Architecture B keeps horizontal sector yaw and uses an **off-axis perspective frustum** for each vertical slab. For output ray `theta=(x-Cx)/f`, `v=(Cy-y)/f`, horizontal-sector offset `delta=theta-center`, and perspective vertical coordinate `q=v/cos(delta)`. A tile identity is `(global horizontal sector index, integer vertical band k)`. Illustrative bands have `q` center `k`, pitch 1.0 and support `[k-0.6,k+0.6]`. Each target is `ceil(2 f tan 35 deg)` by `ceil(1.2 f)`, or 2163x1853 at the fixed reference focal. The vertical frustum is asymmetric for nonzero `k`; merely pitching a symmetric camera changes the ray map and would need different UV and coverage proofs. Adjacent bands overlap by 0.2 in `q`. One deterministic owner band must be selected in the overlap, with a small filter/guard margin; simply sampling whichever target is currently present can pop. The current eight-sampler shader and `ensureSectors` cannot express this grid as-is.

The unbent output rays and the black-hole geodesic/disc equations can remain algebraically unchanged. The source lookup, inverse projection, tile-camera LOD frusta, base/deflected background paths, and source-selection uniforms must change together. The lens needs to select from the **deflected direction** after geodesic integration, using circular horizontal distance and the same `(sector,k)` registry in every context. At angular wrap, normalize delta with `atan(sin(raw),cos(raw))` before UV calculation. At a band boundary, compute `q` from the chosen horizontal sector and use a deterministic boundary convention. A cube fallback with different raster, projection, culling or sampling can reproduce R8; absence of a tile must be an explicit coverage failure or use a globally identical fallback representation. Full 360-degree lens coverage at star-preserving density may cost far more than the table's direct-output-only counts. A proven conservative lens envelope or selective equivalent representation is unresolved.

Global identities must be computed once from the shared primary anchor, focal, sector phase, band phase, and scene pose. Local contexts may allocate only needed instances, but any two contexts that can sample the same direction at a physical join must have the same tile identity, projection, raster, filtering, MSAA, LOD and scene state. The R8 forced-path equality shows why this is a correctness requirement. Source rendering is currently duplicated between contexts; shared identity does not share GPU textures across WebView2 WebGL contexts.

Architecture C would use a directional atlas, texture array, or cube-based representation. A texture array could reduce sampler count if WebGL2 layer and render-target support and Three.js plumbing are verified; it does not reduce total source pixels or render passes and adds layer/resolve complexity. A 2D atlas trades sampler count for atlas dimensions, padding, mip/filter seams and potentially huge sparse surfaces. A cube-only source could make wrap and selection uniform but its 512-face fallback is visibly unlike sector sampling in R8; a high-resolution cube needs six scene passes per context, potentially large face textures, and a directional sampling/LOD/star-quality proof. None is presumed cheaper or equal quality. Screen-fixed blending is rejected by R12's ghosting and new join errors.

## Layout model and resource comparison

The layouts and primary flags are exactly those in `Screensaver/development/r18_model.py` and `r18-model.json`: single 3840x2160; observed 8320x2160 three-monitor; a hypothetical 3840x2160 directly above the left display (8320x4320); the existing layout plus 1920x1080 to the right (10240x2160); and R18's illustrative asymmetric 9600x3600 arrangement. The latter has a 1920x1080 primary, so the fixed-1440 focal is a deliberate policy choice, not its native-height focal. R13's actual normalized rectangles are left `(0,0,3840,2160)`, primary `(3840,720,2560,1440)`, right `(6400,1080,1920,1080)`.

For A, the table uses the **current bounding-height** policy and existing 60-degree source. `A targets` is the R18 source-derived value. For B, it uses the primary anchor/fixed focal above, selects the R18 horizontal sectors overlapping each 512-pixel padded monitor, clips each sector to its nearest-center cell, and includes the minimal contiguous integer bands around band 0 needed to cover that cell's conservative `q` extrema. This deliberately includes some duplicate renders in overlap. `B globals` counts unique `(sector,k)` identities, while `B instances` sums allocations across windows. Neither A nor B count additional lens-deflected coverage. C is the R18 single-tall-source control under the same primary anchor/focal as B. All dimensions are pixels per target. Nominal storage uses RGBA16F color plus depth, one resolved copy and two multisample copies, **36 bytes per source pixel**; it excludes cube, bloom, post buffers, browser surfaces, scene assets and driver overhead. A 4x model is 60 bytes/pixel; no-MSAA is 12 bytes/pixel before driver differences.

The B per-window sampler pressure is therefore 9, 8/8/4, 12/8/8/4, 8/8/6/6, and 6/6/15/4 source tiles respectively, **plus** the lens cube and any other shader samplers. These are direct-output tile counts; lens coverage may increase them. A currently binds eight source sampler slots plus a cube in the lens material, even when fewer sectors exist. A direct B array is already outside that shader's fixed eight slots in the single, fourth-above and mixed cases. Multi-pass composition, texture arrays or atlas indirection would add work and complexity; no sampler-fit claim follows from WebGL2 support alone.

With the black hole enabled, A and B add six cube-face scene renders **per window** to their perspective passes: A totals 8/26/31/35/30 scene renders for the five layouts, and B totals 15/38/56/52/55. C totals 9/28/38/38/37. Without a black hole, the respective perspective-instance counts alone apply. These are pass counts, not measured draw counts. R9 observed 14 extra draws for one added sector in one frozen three-monitor scene; extrapolating that exact number to every band would be unsound because frustum culling, scene objects and tile LOD can vary. B's increased pass count is nonetheless a clear workload risk, especially with overlapping bands and duplicated windows.

Relative to R13 three-monitor output, fourth-above physical pixels rise 59%, while A nominal sector storage rises 250%, C rises 250%, and B rises 60%. B's perspective instances also rise 60%, from 20 to 32; its allocation growth tracks output better but at an already higher three-monitor baseline and with unpriced lens coverage. Four-horizontal physical pixels rise 15%; A storage rises 38%, C 40%, and B 40%. The mixed layout has only 9% more physical pixels than R13 three but considerably different geometry and 31 B instances; it is not a pixel-proportional result. At 4x MSAA, multiply table sector MiB by about 1.67; at no MSAA by about 0.33. R15 measured substantial 4x-to-2x savings, but actual allocations can differ from this simple target model.

The fixed-1440 policy changes object size on the existing layout, unlike R13. If R13's 2316-pixel focal is held instead, each B tile becomes about 3244x2780 and the band counts and memory must be recomputed; the table cannot be used to claim preservation of R13 visual scale. Conversely, changing focal solely to reduce target allocation violates the visual reference constraint. The source size and focal decisions must be accepted separately.

## Correctness, gaps and practical limits

- **R8/R9 parity:** B can remove the sector-versus-cube branch mismatch only if every relevant deflected direction resolves to the same fully rendered representation in both contexts. Global IDs alone are insufficient. The current source has distinct `baseBackground` and `background` selection rules, and the cube fallback remains. R9's frozen fix cost another pass and target; R10 did not establish a motion-safe entry/exit rule.
- **R10 popping:** A band entering or leaving a local allocation must not change the source chosen at a ray already visible on a neighboring monitor. Use conservative lens and bloom/guard coverage, stable ID tie-breaking, and hysteresis only if it does not make contexts disagree. A static tile set for a fixed layout avoids allocation churn but can be expensive.
- **R11 caustics:** A real adjacent-ray gradient can cross a monitor join even with exact source parity. Source-trace equality and within-context neighboring-ray tests are required before calling a bright line a tiling seam.
- **R12 blending:** Blending in physical screen coordinates would create fixed ghosting. Any overlap transition must be defined in angular source coordinates, use equivalent samples, and be checked during motion. Hard selection may still reveal differences in culling, MSAA, star footprint and projection.
- **Joins, bloom, guard:** Horizontal and vertical adjoining output pixels share rays only if every context uses the same optical anchor and focal. This is a geometry condition, not final-pixel proof. Native bloom and the accepted fixture's 512-pixel guard still need consistent offscreen padding and aligned crop/mips. The code's default guard constant is 128; R13-R18 fixtures used 512. Source tiles do not reduce bloom/post allocations.
- **Stars and planets:** Center density of about one is only a first-order invariant. Perspective density changes with `delta` and `q`; vertical slab boundaries, off-axis point sprites, LOD frusta, resolves and filtering can broaden stars or soften planet limbs. R17 demonstrates that density loss matters. A rendered source-parity and slow-motion native-pixel comparison is mandatory.
- **Unused regions:** Empty virtual gaps can be excluded from direct-output source coverage. The padded guard may still overlap a gap, and lens rays can land anywhere. Dynamic omission based only on current visible pixels risks pops. A conservative static coverage union can exclude gaps while retaining lens envelope, but its actual size is unknown.
- **WebView2/WebGL:** WebView2 uses Edge's multiprocess GPU-backed renderer and each control/context has overhead. The code requires WebGL2 and `EXT_color_buffer_float`, and checks `MAX_TEXTURE_SIZE`; actual `MAX_TEXTURE_IMAGE_UNITS`, `MAX_ARRAY_TEXTURE_LAYERS`, `MAX_RENDERBUFFER_SIZE`, `MAX_SAMPLES`, framebuffer completeness and context-loss behavior must be queried in the disposable target WebView2 windows. No universal WebView2 tile/target budget is established. See [Microsoft WebView2 performance guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance), [WebView2 process model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model), and the [Khronos WebGL 2 specification](https://registry.khronos.org/webgl/specs/latest/2.0/). The isolated Stage 2A fixture recorded `MAX_TEXTURE_SIZE=16384` and `MAX_RENDERBUFFER_SIZE=16384` on the owner's setup; that is one observed device, not a support guarantee.

The known coverage gaps are lens-deflected directions outside selected physical-output bands, extreme vertical `q` near sector edges, circular horizontal wrap, source mismatch at band boundaries, and shader sampler capacity. The table does not cover those cases. The mixed case's 15 local source tiles is especially close to or beyond practical direct sampler use once the cube and other uniforms are included. A high-resolution cube or array representation would need its own resource and quality model.

## Smallest isolated proof if research continues

Before any pilot, first revise the band layout on paper to reduce the existing-layout pass count and define a conservative deflected-ray envelope. Reject the design if it still needs roughly twice the three-monitor source passes for little or no baseline memory saving. If that passes, the smallest developer-only experiment would use one frozen current-layout black-hole scene and one vertical-layout simulation with disposable profiles, no owner journey, production code or display changes:

1. Lock one shared primary X/Y anchor and focal, then render a single-tall-source control and a two-axis source at the same rays, full center density and 2x MSAA. Include the R13 full-resolution captures separately as appearance reference.
2. Trace original and deflected rays, tile ID, UV, validity, fallback branch and sampled linear RGB on both sides of horizontal and vertical joins, through angular wrap and at band boundaries. Require same-direction cross-context source parity and no magenta/coverage holes across a yaw sweep.
3. Capture complete native final frames plus slow star, planet-limb and black-hole motion, with native bloom and 512-pixel guard. Inspect small stars and R8-R12 failure states at source and final output; obtain owner visual review before any appearance claim.
4. Measure warmed PID-attributed dedicated GPU memory, target dimensions/samples, GPU context losses, WebGL errors, actual scene/draw calls per window, and GPU work with a reliable timestamp or graphics trace. Browser callback cadence alone is insufficient. Compare growth against physical output pixels and the same-anchor single-tall control.

No pilot is implemented in R19. B1 remains NO-GO until source parity, visual quality, allocation and throughput are all demonstrated on rendered evidence.
